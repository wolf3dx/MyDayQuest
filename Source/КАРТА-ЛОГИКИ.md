# My Day Quest — карта логики

Документ описывает, из чего состоит приложение и как части связаны между собой.
Требование базового правила 4: в `Source` лежит исходный код с комментариями и эта карта.

## 1. Что делает приложение

Планировщик дел в трёх уровнях:

```
Лист (Quest)  →  Задание (QuestTask)  →  Подзадание (Subtask)
```

- **Лист** — конечный набор заданий по одной крупной цели («Карнеги Quest»).
- **Задание** — единица, у которой есть даты начала и дедлайна и прогресс в процентах.
- **Подзадание** — шаг задания; прогресс задания = выполнено подзаданий / всего.

Отмеченные галочкой задания попадают в **дневной план** — главный экран приложения.
Больше **четырёх** заданий в план не берётся (`AppDatabase.DailyTaskLimit`).

## 2. Проекты решения

`Source/MyDayQuest.slnx` содержит три проекта:

| Проект | Назначение | Платформы |
|---|---|---|
| `MyDayQuest.Core` | Модели, база, синхронизация, обновление, облака. UI-фреймворков не знает. | net10.0 |
| `MyDayQuest` | Голова на .NET MAUI | Windows, Android, iOS, macOS (MacCatalyst) |
| `MyDayQuest.Avalonia` | Голова на Avalonia | Windows, Linux, macOS |

Обе головы переиспользуют `Core` и отличаются только слоем представления.
Путь к базе задаёт голова: MAUI — `FileSystem.AppDataDirectory`,
Avalonia — `%APPDATA%`/`~/.config` + `MyDayQuest`.

## 3. Ядро (`MyDayQuest.Core`)

```
Models/            Quest, QuestTask, Subtask — строки таблиц SQLite
Data/AppDatabase   единственная точка записи; Uid (GUID) и UpdatedUtc у каждой строки
Data/SyncService   экспорт/импорт всего дерева в JSON-файл .mdq, отпечаток содержимого
Data/SyncModels    DTO файла синхронизации (SyncFile → SyncQuest → SyncTask → SyncSubtask)
Data/UpdateService проверка новой версии через публичный GitLab Releases API
AppVersion         текущая версия из AssemblyInformationalVersion
Data/ISyncTarget   куда синхронизируемся: FileSyncTarget (путь) или документ
                   облачного диска (реализация в голове, см. раздел 4)
```

Ключевые решения:

- Вся запись идёт через `AppDatabase`, поэтому синхронизация видит любые изменения.
- `UpdatedUtc` проставляется при каждой записи — по нему решается, чьи данные свежее.
- Колонки, добавленные позже, заполняются в `BackfillAsync` **чистым SQL**: чтение
  объектов упало бы на `NULL` в не-nullable `DateTime`.
- Версию для проверки обновлений берём из `AppVersion.Current`, а **не** из
  `AppInfo.VersionString` — на Windows тот отдаёт версию WinUI-пакета.

## 4. Синхронизация через облачный диск

Синхронизируется не база `mydayquest.db3`, а один файл `MyDayQuest.mdq` — всё дерево
листов, заданий и подзаданий в JSON. Он кладётся в облачный диск, а дальше его
разносит сам диск.

```
ISyncTarget        куда писать: Describe / ExistsAsync / ReadAsync / WriteAsync
FileSyncTarget     обычный файл по пути — настольные ОС и папка клиента диска
SafSyncTarget      (в MAUI-голове) документ облачного диска на Android
SyncTargetStore    (в MAUI-голове) выбор файла и память о нём
```

Кнопки: **Load** открывает файл и запоминает его, **Sync** обновляет именно его,
**Save** создаёт новый файл.

Как решается, кто кого перезапишет:

1. Цели нет или файл пуст — данные выгружаются.
2. Отпечатки содержимого совпали — ничего не делаем. Сравнение идёт **по содержимому,
   а не по времени**: штамп в файле после выгрузки всегда свежее последней правки,
   и сравнение по времени одно гоняло бы данные обратно при каждом следующем Sync.
3. Иначе побеждает тот, кто изменён позже.

После записи файл читается обратно и содержимое сверяется. Это не перестраховка:
поставщик документов может принять запись молча и никуда её не отправить — без
проверки это выглядело бы как успешная синхронизация, а изменения пропадали бы.

Повадки Android (проверено на Samsung M31s, Android 12, OneDrive):

- `FilePicker` из MAUI **не годится** — он отдаёт копию файла в кэше приложения,
  запись в неё никуда не уезжает. Нужен свой `ACTION_OPEN_DOCUMENT` с
  `takePersistableUriPermission`, иначе ссылка умрёт вместе с окном выбора.
- Поток на запись открывается в режиме `"wt"`: без `t` поставщик оставляет хвост
  прежнего, более длинного содержимого.
- Создать файл в OneDrive с телефона нельзя — в режиме создания системный проводник
  его не показывает. Файл создаётся на компьютере, с телефона только открывается.
- Выгрузка в облако идёт с задержкой, в проверке — около четверти часа.
- Разрешение теряется при переустановке приложения: надо один раз выбрать файл заново.

## 5. Головы

### MAUI (`Source/MyDayQuest`)

```
MauiProgram        сборка DI: AppDatabase, SyncService, UpdateService
MainPage.xaml      главный экран: шапка, среднее поле, лента закладок листов
ViewModels/MainViewModel   состояние экрана и все команды
ViewModels/*VM     модели плашек: QuestTab, TaskItemVM, DailyTaskVM, SubtaskVM
Views/TaskDetailPage   карточка задания: даты, прогресс, подзадания
Views/AboutPage        о приложении и авторе
Services/SyncTargetStore       выбор файла синхронизации и память о нём
Platforms/Android/SafSyncTarget  чтение и запись документа облачного диска
```

### Avalonia (`Source/MyDayQuest.Avalonia`)

```
App.axaml.cs       сборка зависимостей вручную (без контейнера)
MainWindow.axaml   тот же экран средствами Avalonia
Dialogs.cs         модальные окна: ввод, подтверждение, выбор из списка
ViewModels/        свои модели представления поверх общего Core
```

Голова Avalonia инициализирует SQLite явно: `Batteries_V2.Init()` в `Program.cs`.

## 6. Экраны

- **Главное окно** — дневной план: плашки отмеченных заданий, у каждой лист-источник,
  текущее подзадание с галочкой, сроки и полоса прогресса.
- **Открытый лист** — задания выбранного листа. Одиночный тап выделяет (для удаления),
  двойной открывает карточку задания.
- **Карточка задания** — имя, дата старта, дедлайн, прогресс и список подзаданий.
- Кнопки среднего поля контекстные: `+` добавляет лист либо задание, `–` удаляет
  выбранное, **QUEST** сворачивает лист и возвращает на главное окно.

## 7. Оформление

Палитра и стили — «журнал заданий»: тёмная кожа обложки, пергаментные плашки,
золотые рамки, медальон со знаком «!». Цвета в `Resources/Styles/Colors.xaml`,
текстуры в `Resources/Images`. Шрифт серифный **системный** (Georgia / serif) —
файлы шрифтов в репозиторий не кладутся. Графика нарисована с нуля; приложение
не связано с Blizzard Entertainment и не использует её материалы.

## 8. Сборка выпуска

Базовое правило 9 — обе архитектуры, x64 и ARM64:

| Платформа | Чем собирается | Артефакт |
|---|---|---|
| Windows x64 / ARM64 | MAUI, `-r win-x64` / `win-arm64`, self-contained | zip |
| Linux x64 / ARM64 | Avalonia, `-r linux-x64` / `linux-arm64`, self-contained | tar.gz |
| Android (arm64-v8a, armeabi-v7a, x86, x86_64) | MAUI, `-f net10.0-android` | apk |
| macOS x64 / ARM64 | GitHub Actions, `apple-build.yml` | zip с .app |
| iOS arm64 | GitHub Actions, неподписанный | ipa (ставится через AltStore) |

Основной репозиторий — GitLab. GitHub используется **только** для сборок Apple.
